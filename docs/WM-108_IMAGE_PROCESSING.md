# WM-108 — Moments image processing spike

Date: 2026-08-31

This is a decision record for WM-108. It does not add the production WM-109
upload pipeline and it does not modify the existing Admin image-storage
function.

## Scope gate

The checked-in V1 product definition still excludes public accounts and social
features. The WeMilkTea v1.4 WM-108 ticket explicitly authorizes this technical
spike, but this note does not update `docs/PRD.md`, approve a public launch, or
authorize WM-109. The product owner must approve the v1.4 scope and update the
product definition before this technical recommendation is treated as an
implementation decision.

## Decision

Use a hybrid pipeline for WM-109:

1. Normalize in the real browser with `createImageBitmap`, applying image
   orientation, drawing pixels to a canvas, and encoding one normalized WebP.
2. Upload only that normalized candidate to a short-lived R2 quarantine key
   generated by the server.
3. Server-side authorization, byte checks, decode/dimension verification,
   normalized-output limits, and WebP metadata checks remain mandatory. A
   client must not be able to finalize an `image_assets` row by claiming that
   it normalized an image.
4. Bind validation and promotion to the same object version. The server must
   capture the quarantine object's ETag/version and either conditionally copy
   that exact version into a unique server-only validation key before checking
   it, or use an equivalent ETag/version precondition for the final copy. If
   the precondition fails, reject or restart the upload. Never unconditionally
   re-read or copy the client-writable quarantine key after validation. Promote
   only the exact validated object, then finalize the owned draft with
   server-observed metadata. Delete rejected or abandoned quarantine objects.

The preferred verifier is a small Cloudflare Worker using the existing R2
account plus the current Images binding `info()` operation. It gives the
server a documented decode/format/dimension check without placing native
`sharp`/libvips in a Supabase Edge Function. WM-109 must still prove the
configured binding's failure behavior and enforce the application limits before
finalization. If that binding is not available to the project, a separate
Deno/Wasm verifier spike is required before selecting a Supabase Edge Function
implementation.

The final object key should be server-generated, for example:

```text
community/{owner-user-id}/{post-id}/{image-id}.webp
```

The browser never chooses the user-id, post-id, image-id, or final prefix.
Existing Product/Store Admin key conventions remain unchanged.

## Prototype

The committed prototype is deliberately dependency-light:

- `spikes/wm-108-image-processing/browser-normalization.html` runs in a real
  browser. It fetches fixtures as `Blob`s, inspects JPEG/PNG/WebP header
  dimensions and applies byte, dimension, and pixel guards before calling
  `createImageBitmap(source, { imageOrientation: "from-image" })`. It repeats
  the dimension/pixel checks after decode, then downscales to the requested
  long edge, draws to a normal 2D canvas, and calls `canvas.toBlob()`.
- `generate-fixtures.mjs` creates synthetic JPEG, PNG, WebP, portrait,
  landscape, EXIF/GPS, and malformed fixtures with the locally installed
  `ffmpeg` and `cwebp` binaries. The EXIF/GPS values are synthetic and contain
  no personal data.
- `inspect-metadata.mjs` parses JPEG/PNG/WebP container metadata and uses
  `ffprobe` to confirm that an output has a positive-dimension image stream.
  It is a spike verifier, not production upload code.
- `serve-harness.mjs` serves the HTML and fixtures on loopback for browser
  execution.

No npm package was added. The executed browser was Chromium 151 on macOS,
with native `createImageBitmap`, canvas `toBlob`, and WebP encoding available.

## Results

The primary run used WebP quality `0.85`, a 2048px maximum long edge, a 10 MiB
source-byte guard, and a 40,000,000 decoded-pixel guard.

| Input                 | Input bytes |                   Decoded dimensions |               WebP output | Browser time |
| --------------------- | ----------: | -----------------------------------: | ------------------------: | -----------: |
| Normal JPEG           |     109,879 |                          1600 × 1200 | 53,574 bytes, 1600 × 1200 |      66.9 ms |
| Transparent PNG       |       3,270 |                            800 × 600 |    1,902 bytes, 800 × 600 |      16.2 ms |
| WebP source           |      53,078 |                          1600 × 1200 | 50,834 bytes, 1600 × 1200 |      58.5 ms |
| Large landscape JPEG  |     538,259 |                          4032 × 3024 | 89,340 bytes, 2048 × 1536 |     127.2 ms |
| Large portrait JPEG   |     548,714 |                          3024 × 4032 | 87,150 bytes, 1536 × 2048 |     134.6 ms |
| EXIF/GPS JPEG         |       2,549 | 400 × 300 source; 300 × 400 oriented |    1,018 bytes, 300 × 400 |       4.5 ms |
| Malformed `photo.jpg` |          19 |                          not decoded |                  rejected |       0.1 ms |

The synthetic EXIF/XMP fixture contained Orientation 6, camera make/model, and
synthetic GPS coordinates. The output pixel quadrants were blue/red/yellow/green
from top-left clockwise, proving that orientation was applied before metadata
was discarded. Independent inspection found WebP chunks `VP8X`, `ICCP`, and
`VP8 ` (plus `ALPH` for the PNG output), with no EXIF or XMP chunks and no GPS.
The remaining ICC color profile is not location metadata.

The WebP output for the alpha fixture had transparent corners and an opaque
red center (`cornerAlpha = 0`, `centerAlpha = 255`). JPEG output had no alpha
(`cornerAlpha = 255`), so WebP is the better single output format for the
supported input set.

The same browser run with JPEG output produced 91,779 bytes for the normal
fixture, 133,869 bytes for the large landscape, 126,000 bytes for the large
portrait, and 7,043 bytes for the transparent PNG. Those JPEG outputs decoded
successfully and contained no EXIF/GPS, but they lost transparency.

These are representative synthetic-fixture measurements on a desktop, not a
mobile benchmark or a quality laboratory. Mobile performance still needs a
WM-109 device pass.

## Guard experiments

The browser harness rejected a 4032 × 3024 image before `createImageBitmap` when
its test limit was set to 10,000,000 pixels, with:

```text
Header pixel count exceeds 10000000 pixels (4032×3024).
```

The same preflight rejected the large landscape before decode when the
dimension limit was set to 3,000px. It also rejected the 109,879-byte normal
JPEG before decode when the test byte limit was set to 100,000 bytes. The
malformed fixture was served as `image/jpeg` from a `.jpg` URL and was rejected
by the header check. These checks reduce client-side decompression pressure but
cannot be trusted against forged headers; WM-109 must repeat them and perform
authoritative decode verification at the server boundary.

## Limits recommendation

For the Moments MVP:

- source bytes: 10 MiB, aligned with the existing image-storage policy;
- decoded dimensions: reject any dimension over 8,000px or a decoded pixel
  count over 40,000,000;
- output: WebP, maximum long edge 2,048px, quality `0.85`, preserving alpha;
- accepted source formats: JPEG, PNG, and WebP. Do not silently promise HEIC
  support until it has a separate browser/device test;
- final content type: exactly `image/webp`.

The 40MP limit supports ordinary 12MP-class phone photos while bounding
decompression risk. It intentionally does not promise every 48MP/108MP camera
mode for the MVP. The server must apply the source-byte, decoded-dimension, and
decoded-pixel limits, plus independently enforce the final normalized-output
limit of a 2,048px maximum long edge. A valid WebP over 2,048px is still not a
valid final asset. The server must not trust client-supplied width, height, or
MIME declarations.

## Options evaluated

### Supabase Edge Function processing

Feasible in principle with a carefully bundled Wasm decoder/encoder, but not
selected. Current Supabase limits document 256 MiB hosted memory, 2 seconds of
CPU time per request, a 5 MiB server-side bundle limit, and no Web Worker or
Node `vm` support. The same limits documentation calls out `libvips` and
`sharp` as examples of libraries whose multithreading is unsupported. Supabase
Wasm modules are supported, while the current Wasm guide still documents the
hosted runtime as Deno 1.46. This repository's environment has no Deno or local
Supabase runtime to prove a large-phone-image decoder/encoder inside the hosted
Edge Function limits. Native `sharp` is therefore not an evidence-based choice
for this task. The Edge Functions changelog has newer runtime preview entries,
so WM-109 must verify the deployed runtime rather than infer compatibility from
the changelog alone.

### Browser processing

Actually tested and successful for all valid fixtures. It performs a bounded
JPEG/PNG/WebP header preflight before browser decode, avoids sending the large
source decode to the server, reduces upload size, and removes EXIF/GPS by
re-encoding pixels. It is not an authority: a malicious client can skip the
browser or send forged headers, and a browser decoder can still encounter
malformed content. The server must validate the candidate independently. The
harness also checks the returned Blob type because canvas may fall back to PNG
when a requested encoder is not available.

### Cloudflare processing

Research-only in this repository. The current Images binding accepts raw image
bytes, exposes a free `info()` operation for format/size/dimensions, and can
produce WebP output. It has a documented 20 MB binding input limit and uses
Cloudflare's Workers limits, including 128 MiB per-isolate memory and
plan-dependent CPU/request limits. The binding's `info()` call is documented as
free, while unique transformations are billable. It requires an Images
binding/account configuration and introduces vendor/cost coupling. Cloudflare
Polish documentation also does not guarantee removal of every metadata field,
so Polish alone is not an EXIF/GPS privacy boundary.

### Hybrid

Recommended. Browser normalization handles the common, expensive path and
privacy reduction. A Cloudflare-side verifier remains authoritative for
ownership-independent byte/decode/dimension checks, metadata allowlisting, and
quarantine-to-final promotion. This keeps arbitrary client bytes out of the
final namespace without forcing native image libraries into Supabase Edge
Functions.

## WM-109 responsibility boundary

Browser responsibilities:

- select a supported source file;
- decode with real image APIs and apply orientation;
- enforce client-side byte/pixel UX limits;
- resize and encode WebP at the agreed quality;
- report the actual output Blob type, byte length, and dimensions.

Server responsibilities:

- require the authenticated owner identity only at the first write action;
- authorize the owned draft and derive the quarantine/final object key;
- bind validation and promotion to one object version with an ETag/version
  precondition or an immutable server-controlled copy;
- issue a short-lived, single-object upload authorization;
- check object existence, exact content type, byte length, magic bytes, and
  server-observed dimensions;
- decode/verify the candidate with the selected server verifier;
- reject EXIF/XMP/unknown WebP metadata chunks and enforce the source pixel and
  final 2,048px long-edge limits;
- finalize `image_assets` and transition the draft only after valid verification;
- delete rejected/expired quarantine objects.

R2 responsibilities:

- hold a short-lived quarantine candidate and the final normalized WebP;
- enforce object-key separation and cleanup;
- never be treated as proof that bytes are an image merely because a PUT
  succeeded.

## Security consequences

WM-109 must reject all of the following at the server boundary:

- arbitrary bytes or a filename/MIME spoof: require RIFF/WEBP magic and an
  independent decode/format check;
- a client-supplied JPEG/PNG in the final path: require exact WebP output;
- a valid WebP over the 2,048px final long-edge limit: reject it even when it is
  below the broader 8,000px/40MP source-safety limits;
- an object over 10 MiB: reject and delete before finalization;
- dimensions over 8,000px or 40MP: reject and delete based on decoded/server
  metadata, not the request body;
- EXIF/GPS/XMP-bearing WebP metadata: reject forbidden/unknown metadata chunks;
- an object belonging to another user/post: reject the signed-key request and
  protect draft finalization with owner RLS/RPC checks.

## Running the spike

The generator requires `ffmpeg` and `cwebp`. Start the loopback server with a
shared temporary directory, then open the printed URL in a real browser:

```sh
node spikes/wm-108-image-processing/generate-fixtures.mjs /private/tmp/wm108-fixtures
node spikes/wm-108-image-processing/serve-harness.mjs /private/tmp/wm108-fixtures 8787
```

Example browser query:

```text
http://127.0.0.1:8787/?fixtures=normal-photo.jpg,transparent.png,photo.webp,large-landscape.jpg,large-portrait.jpg,orientation-exif.jpg,photo.jpg&maxLongEdge=2048&maxPixels=40000000&quality=0.85&format=image%2Fwebp&includeBytes=0
```

Inspect captured output bytes with:

```sh
node spikes/wm-108-image-processing/inspect-metadata.mjs /private/tmp/wm108-normal-photo.webp /private/tmp/wm108-transparent.webp /private/tmp/wm108-orientation-exif.webp
```
